# 网页桥接思考期报活

## Why

本地工作区在 DeepSeek 网页模式下分析时，会在跑到一半时报「连续 3 分钟没有产生新内容」而中断。

根因是两端的超时互不知情：

- content script 的 `waitReply` 只在检测到回复文字增长时才推送 `delta`，其余时间静默轮询，自己的耐心上限是 600 秒
- 扩展侧只有收到 `delta` 或 `progress` 才刷新活动时间，超过 180 秒即判死

DeepSeek 进入深度思考时，思考内容不在回复容器里，`getAssistantTexts()` 会把空文本过滤掉，于是整个思考阶段一个消息都发不出去。只要首字延迟超过 3 分钟，一个还在正常思考的请求就会被判死。

本地工作区尤其容易撞上：GitHub 网页模式走的是一次请求直答，而本地工作区走逐轮 JSON 工具往返，每一轮都是一次独立的「等首字」窗口，任何一轮超时就整体失败。

## What

- content script 在页面确实处于生成状态、但正文尚未出现时，每 15 秒推送一次思考进度
- 页面既没有在生成、又没有新内容时保持静默，让空闲超时如实触发
- 空闲超时文案改为描述真实状态（页面没有任何动静），并给出可操作方向

## Not

- 不改动 180 秒空闲阈值与 600 秒硬上限
- 不改变本地工作区的逐轮工具协议（把它也改成一次请求直答是另一件事，需要单独评估，因为写回依赖受约束工具）
- 不新增对 DeepSeek 思考内容容器的选择器依赖，只用现有的生成状态判定

## 验收

1. DeepSeek 思考超过 3 分钟后才开始输出时，分析继续进行而不是中断
2. 思考期间侧栏显示已等待秒数，而不是长时间无反馈
3. 页面卡在登录、风控或排队而完全没有动静时，仍在 3 分钟后报错
4. `pnpm test` 通过，其中包含「持续报活不判死 / 毫无动静则判死」两条用例
